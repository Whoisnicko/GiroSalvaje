# Campaign Architecture & Save System — v22-alpha.7.14

Roadmap step 3. Foundation only: no route selection, map rendering, new currency, shop restriction, balance, tutorial or artwork changes. The original ten-wave combat remains intact.

- New `engine/campaign-save.js`: version-15 campaign snapshots retain existing battle state; metadata version 1 stores stable campaign ID, 32-bit seed, reserved node/route fields and claimed wave rewards. Node is null and route empty until the map phase. Snapshots are detached JSON data. Existing v14 save is migrated on Continue; original raw save is retained in `gs22.legacySave.v14` before first write, and upgrade is stopped if that copy cannot be protected. The canonical campaign key remains `gs14.save` for discovery. Existing legacy save validation is strengthened, not a comprehensive validation of hostile input.
- Permanent starting deck and one end-of-run card receipt per campaign share `gs22.campaignProfile.v1`; legacy deck duplicates are preserved. A failed profile write does not grant a card. Spell knowledge/mastery and martial talents retain their established independent authoritative stores. Exports include all three, and a profile-only export works without an active campaign. Import merges permanent progress, does not delete learned content; legacy base decks merge by maximum copy count per card, receipts by run ID, conflicting receipts keep local choice. Separate storage writes for spell/talent/deck are not a cross-key transaction; an interrupted import may be incomplete and can be retried.
- Legacy terminal saves have no way to tell whether their final card was already collected; they are archived without an additional claim (an unclaimed legacy reward can therefore be forgone). Legacy active/reward saves retain their army, souls, hero, world width, and valid existing cards. Prior v14 backup files without permanent deck data cannot reconstruct missing decks on a fresh browser.
- Wave reward selection checks the phase and records the completed wave in the same snapshot. Restore uses the saved wave for dynamic card descriptions (fixes previously possible restore crash). Existing autosave in stable states, 5-second interval, visibility changes and pagehide retained. No saves during spin/drag/merge or relic selection; reload resumes the last valid snapshot, not necessarily every transient combat frame. Pending random actions are not secured against intentional rollback. Sandbox remains isolated. Local single-browser/single-tab only; backups do not provide cloud sync or tamper-proof rewards across devices.

Validation: actual engine in Chromium 1366x768 with inline assets, simulated localStorage (HTTP navigation blocked by environment). Tested new run, v14 migration and original backup, legacy duplicate deck, preparation reload after purchases, pending wave reward restore and selection, terminal receipt after reload and older backup restore, idempotent profile merge, Warlord fight resume, simulated failed receipt write/retry, Sandbox isolation, spell/talent retention, unknown schema rejection and legacy terminal archival. No JS errors in final run. Wave completion/defeat invoked in test rather than played through naturally. Some assets may use fallbacks. Not tested: deployed Cloudflare, real persistent browser storage, file picker/download on a normal browser, simultaneous tabs or complete campaign.

Next: roadmap step 4, Underworld Journey. Use stable seed/ID and route metadata; add checkpointed map choice and node resolution without changing Hades availability until route economy is balanced.
